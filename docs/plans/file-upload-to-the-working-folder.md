A first, abandoned attempt (client-supplied folder, base64 chunks, 25 MiB) left about 127 lines of message types in a git stash named "upload protocol draft (superseded by roadmap R78)" (`git stash list`); it is a hint for naming, not a base to build on, because its `UploadStart` took a `dir` from the client, which the decision forbids.

Design in one paragraph: the client names a workspace and tab and a list of files. After the user confirms on a sheet, the server resolves the tab's live working folder (tmux `pane_current_path`, already tracked in `packages/server/src/control.rs` and `backend.rs`), canonicalises it, refuses unless under `$HOME`, pins it, and replies `upload_ready` with the folder. Bytes follow as binary chunks with a byte-bounded window into a hidden temporary file, which is moved into place at finish (Keep both, Replace or Skip chosen per file). A dropped connection keeps the partial for 10 minutes and `upload_resume` continues from the server's offset. One file at a time, 60 starts a minute, 100 files per batch, a 1 GiB free-disk floor, owner only, mode `0600`, content-free audit.

### 2.1 Core messages, binary chunk frame and limits — [x]
Class: implement · Needs: 1.1 · Check: `scripts/dev.sh cargo test -p termenbox-core upload`
Context: `packages/core/src/protocol.rs` defines `ClientMessage` and `ServerMessage` (serde, `#[serde(tag = ...)]`; follow how `ListDir` and `DirListing` are written, around `DIR_LISTING_MAX`). The wire format is mirrored by hand in `packages/client/src/lib/protocol.ts`. DECISION-0194 lists the messages: `upload_start {id, workspace, tab, name, size, collision}` (no folder), `upload_resume {id}`, `upload_finish {id}`, `upload_cancel {id}`, and the replies `upload_ready {id, dir, offset}`, `upload_progress {id, received}`, `upload_done {id, path, size}`, `upload_denied {id, reason}`, `upload_failed {id, reason}`, `upload_cancelled {id}`. `collision` is `keep_both`, `replace` or `skip`. The chunk is a binary frame in the kind step 1.1 chose, carrying the upload id and byte offset.
Do: Add the messages, the chunk frame encode/decode, and the constants `UPLOAD_FREE_DISK_FLOOR` (1 GiB), `UPLOAD_RESUME_GRACE_SECS` (600), `UPLOAD_WINDOW_BYTES` (1 MiB), `UPLOAD_STARTS_PER_MINUTE` (60), `UPLOAD_MAX_BATCH` (100). Add round-trip tests, a test that no message has a path field the client fills, and a test that a chunk over the frame limit is rejected by the decoder.
Done-when: `cargo test -p termenbox-core upload` passes with tests for each message round trip, the frame round trip, an oversize frame and an out-of-order offset; the `UploadStart` struct has no field that carries a folder or path.

Do: In `packages/server/src/upload.rs`, implement `upload_start` (owner only, rate limit, batch limit, free-disk check with `statvfs`, pin the folder, create the hidden `.tb-upload-<random>.part` with `create_new` and mode `0600`), chunk handling (in-order offsets, write at once, reply progress), `upload_finish` (size must equal the declared size; Keep both picks `name (1).ext`, hard link into place so an existing name is never overwritten; Replace renames over the name, never writing through a symlink; Skip deletes the partial), `upload_resume` (continue from the server's offset if the entry is within the grace period), `upload_cancel`, cleanup on error and when the grace period ends, and the audit events. Done-when: `cargo test -p termenbox-server upload` passes with a test for each line of the guardrail's "Checked by", including: a guest is refused, a `cd` after start does not move the file, the created file is `0600`, Keep both never overwrites, a partial is gone after cancel and after the grace period, resume continues from the offset, a start below the floor is refused, the 61st start in a minute is refused, and no audit line contains the name or path.

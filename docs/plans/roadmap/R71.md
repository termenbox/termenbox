## Why

Nightly builds come from `develop` and stable and beta tags from master, so feature work must reach `develop` first and master must move only for a release. A workflow that closes pull requests after they open is brittle (it needs a token, runs after the fact, and blocks its own fix). A repository ruleset enforces the rule at merge time with no code.

## Context

GitHub cannot refuse to open a pull request against a branch; a ruleset limits what can land. Rulesets are free on a public repository. Plan: create `develop` from master; make it the default branch so new pull requests target it; add a ruleset on `master` with "Restrict updates" and the release managers on the bypass list, so a feature pull request can be opened but not merged; add a ruleset on `develop` with required pull request, required status checks (the CI jobs) and `.github/workflows/**` plus `release-keys.txt` under CODEOWNERS. Fast-forward `develop` into master before a release. The default-branch change affects `go-getter` hooks and any docs saying "branch off master", the commit-subject CI and `no-commits-on-the-default-branch`.

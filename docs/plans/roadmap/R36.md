## Why

The application supports desktop Chrome/Firefox/Edge current-2 and Safari 16+, but existing UI scripts create touch/mobile Chromium contexts. WebKit coverage alone leaves desktop keyboard and mouse behavior unchecked.

## Context

`packages/client/e2e/{cards,touch,windows,two-servers,run}.mjs` import Chromium directly. `run.mjs` has transport/resource checks as well as phone scenarios. Preserve those gates; do not multiply the throughput benchmark across every UI variant.

## Do

1. Make the common harness accept Chromium, Firefox and WebKit; add desktop contexts with `isMobile: false`, `hasTouch: false` at 1024x768 and 1440x900. Keep the existing mobile Chromium scenarios and add the original R36 mobile WebKit scenarios where supported.
2. Drive the real client against isolated test servers: attach/reconnect, tab/window switching, sidebar, dialogs, keyboard-only actions, pointer selection, clipboard allowed/denied and terminal mouse reporting. Steps U04, U07c and U15 and R61 each add their own desktop regression scenario and CI invocation in their implementation PR, starting with the existing Chromium job; reuse these scenarios as they land and extend them to Firefox/WebKit. R59 owns a separate real-tmux feasibility experiment. R36 can establish its engine matrix with current behavior and does not wait for future features.
3. Test the 720/721px transition, DPR 1/2 and a resize while a session is active; record a manual desktop browser-zoom check at 200%. Confirm fit rows/columns and that xterm is retained.
4. Enforce the existing bundle threshold from `e2e/check-bundle.mjs`; do not restore the stale 215 KB value from the old ticket.
5. Record browser engine/version, viewport, failure screenshot and trace in CI. Keep real iPhone checks in `docs/skills/mobile-ui-device-check.md`; document actual Safari/Edge and minimum-version checks separately because Playwright engines alone do not prove that support floor.

## Done when

CI covers the desktop flow on Chromium, Firefox and WebKit plus the original mobile checks; a deliberately broken keyboard handler or desktop layout fails a relevant scenario; artifacts identify the failed engine; throughput/resource and bundle gates remain in force. A written compatibility checklist distinguishes engine automation, real desktop browser checks and the owner's real-iPhone checks.

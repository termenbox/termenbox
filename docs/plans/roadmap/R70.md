# R70 Release channels 5: the client shows a newer release for the selected channel

## Why

The server updates itself, but a user on a stable app has no way to see that a beta or nightly exists. The client cannot install a server release; it can only tell the user.

## Context

Settings gets a release channel, remembered in localStorage per origin, defaulting to the build's `VITE_CHANNEL`. Switching it changes what the client reports, not the app: "Beta 0.2.0-beta.2 available" with a link to the beta app, never a reload button. Endpoints (unauthenticated GitHub limit is 60 requests an hour per IP): stable `releases/latest`; beta `releases/tags/channel-beta`; nightly `releases/tags/channel-nightly`, with the version read from the release `name` or `body`. Cache six hours with `ETag` and exponential backoff. The PWA bundle update (`updateAvailable`) and the server release notice are separate states; only the first shows a reload button (R50 notes: a service-worker update in one tab must not reload a live terminal in another).

## Do

`packages/client/src/lib/update.ts` (`checkServerUpdate(channel)`), `settings.ts` (the stored channel), `App.svelte` (a toast apart from the PWA one), tests with a mocked GitHub response.

## Done when

On the stable origin, selecting beta shows the newest beta with a link to the beta app and no reload button; a second call within six hours makes no request; a rate-limit response backs off; PWA reload behaviour is unchanged.

## Check

`pnpm -r test` green in CI; an iPhone check of the toast by platform (guardrail `a-phone-check-names-its-platform`).

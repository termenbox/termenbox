## Why

Today there is exactly one release stream: a `vX.Y.Z` tag triggers `release.yaml`, which builds a signed manifest and publishes a GitHub Release. The server's daily updater fetches `releases/latest/download/manifest.json`, verifies the signature, compares only the core `X.Y.Z` version, and installs if newer. The client is deployed to Cloudflare Pages from `master` on every push.

The owner wants three distinct channels with clear boundaries, independent update policies, and no accidental cross-promotion:

- **stable** — production-ready, manually tagged, auto-update by default.
- **beta** — release candidates and beta tags (`vX.Y.Z-rc.N`, `vX.Y.Z-beta.N`), cumulative with stable, auto-update by default.
- **nightly** — daily builds from `develop`, notify-only by default, never promoted to stable/beta.

Each channel must have its own signed manifest, its own trust anchor, its own Pages deployment, and its own update cadence.

## Design summary (record as decisions before building)

### 1. Tagging and versioning

| Channel | Branch | Git tag pattern | Manifest `version` | Docker tag(s) |
|---|---|---|---|---|
| stable | `master` | `vX.Y.Z` (no suffix) | `X.Y.Z` | `latest`, `X.Y`, `X.Y.Z` |
| beta | `master` | `vX.Y.Z-rc.N`, `vX.Y.Z-beta.N` | same as tag without `v` | `beta`, `X.Y.Z-rc.N`, `X.Y.Z-beta.N` |
| nightly | `develop` | `vYYYY.MM.DD-nightly` | `X.Y.Z-nightly.YYYYMMDD` | `nightly`, `X.Y.Z-nightly.YYYYMMDD` |

- `Cargo.toml` **always** contains only core `X.Y.Z` (no prerelease). Prerelease lives only in the Git tag and the manifest `version`.
- Nightly manifest version uses the Cargo core version + `-nightly.<date>` (e.g., `0.1.36-nightly.20261022`). This makes SemVer ordering work: `0.1.36-nightly.20261022 < 0.1.36-nightly.20261023 < 0.1.37`.
- The `make_manifest.py` script receives a separate `--tag` argument for the Git tag (used in download URLs) and `--version` for the manifest `version` field.

### 2. Three channels, each its own manifest and trust anchor

Three independent Ed25519 signing keys, each bound to a channel:

```text
r1 ssh-ed25519 AAAA... channel=stable
b1 ssh-ed25519 AAAA... channel=beta
n1 ssh-ed25519 AAAA... channel=nightly
```

Trust sets (which keys a binary accepts):

| Binary channel | Accepts keys |
|---|---|
| stable | `r1` only |
| beta | `r1` + `b1` (because `channel-beta` alias may point to a stable release) |
| nightly | `n1` only |

The manifest gains a required `channel` field (`"stable" | "beta" | "nightly"`). The updater verifies the signature **and** checks that the signing key's channel matches the manifest's channel (or, for beta, that the key is in the beta trust set). This prevents a compromised nightly key from signing a stable manifest.

**Key storage:**

- `r1` — GitHub Environment `stable`, protected, required reviewers.
- `b1` — Environment `beta`.
- `n1` — Environment `nightly`, available to `develop` workflow.

Old stable binaries (without channel binding) continue to work because they only know `r1` and will reject `b1`/`n1` signatures. New binaries parse the extended `release-keys.txt` (4th field optional) and enforce channel binding.

### 3. Alias releases (`channel-beta`, `channel-nightly`)

Each channel has a rolling GitHub Release whose tag is the channel name:

- `channel-stable` — not used (stable uses `releases/latest`).
- `channel-beta` — points to the newest beta/rc/stable release by SemVer.
- `channel-nightly` — points to the newest nightly release.

The alias release contains only `manifest.json` and `manifest.json.sig` (clobbered on each update). The manifest inside the alias is a copy of the versioned release's manifest, so its `version` and `channel` reflect the actual release. The updater and installer **must** read asset URLs from the manifest (not construct them from the alias tag), because the binary lives under the versioned tag.

Alias update logic (run in the stable/beta/nightly workflow after a successful publish):

```python
# Pseudo-code for alias update
current = fetch_alias_manifest("channel-beta")
candidate = new_release_manifest
if semver_compare(candidate.version, current.version) > 0:
    update_alias("channel-beta", candidate)
```

Nightly cleanup (keep last 14 days) must **never** delete the release currently referenced by `channel-nightly`.

### 4. Server update policy (per-server config)

Persisted in the server's config directory (root-owned, written by installer/updater):

```toml
[update]
channel = "stable"        # stable | beta | nightly
mode = "auto"             # auto | notify | hold
maintenance_window = "03:00-04:00"  # local time, optional
```

Defaults: `channel = "stable"`, `mode = "auto"`.

Behaviour:

- `auto` — daily timer applies update immediately if manifest is newer and passes health check.
- `notify` — daily timer checks, records available version in status, does not install. Owner triggers via `Request::UpdateNow` (web UI or CLI).
- `hold` — timer does nothing. Owner must change mode or run update manually.
- Cross-channel rules:
  - Stable server never installs beta/nightly.
  - Beta server installs stable (via `channel-beta` alias) or beta/rc.
  - Nightly server installs only nightly.
- Major version bump (`X` in `X.Y.Z`) always requires `mode != "auto"` or explicit owner confirmation (future: protocol version negotiation).

The installer writes the initial config from its `--channel` flag. Changing the channel later is a host-level operation (re-run installer with new `--channel` or edit config + restart updater timer), **not** a web UI action in v1.

### 5. Frontend: three independent Pages deployments

| Channel | Domain | Pages project | OAuth app | Build env |
|---|---|---|---|---|
| stable | `app.termenbox.dev` | `termenbox` | stable | `VITE_CHANNEL=stable`, `VITE_API_ORIGIN=https://app.termenbox.dev` |
| beta | `beta.app.termenbox.dev` | `termenbox-beta` | beta | `VITE_CHANNEL=beta`, `VITE_API_ORIGIN=https://beta.app.termenbox.dev` |
| nightly | `nightly.app.termenbox.dev` | `termenbox-nightly` | nightly | `VITE_CHANNEL=nightly`, `VITE_API_ORIGIN=https://nightly.app.termenbox.dev` |

All three share the same D1 database and `CERT_SIGNING_KEY` / `DIRECTORY_SALT`. `TERMENBOX_GITHUB_CLIENT_ID/SECRET` are per-environment. Deploy is triggered by the channel's workflow (stable on tag, beta on tag, nightly on schedule).

**Why separate origins:** PWA service worker, Cache API, localStorage, and OAuth callback URLs are origin-bound. Path-based channels (`/beta/`) cause cache collisions, SW scope issues, and shared cookies. Separate domains give clean isolation and independent rollback.

### 6. Client update check (informational only)

The client **cannot** install server releases. It only checks GitHub for a newer release in the selected channel and shows a toast/badge. The server updates itself via its own timer.

Channel selection in Settings (persisted in localStorage per origin):

- Default = build-time `VITE_CHANNEL`.
- User can switch to see another channel's status, but the app binary does not change. Switching from stable app to "beta" shows "Beta 0.2.0-beta.2 available" with a link to the beta app, not a reload button.

API endpoints (no pagination issues):

- stable: `GET /repos/termenbox/termenbox/releases/latest` (excludes prereleases).
- beta: `GET /repos/termenbox/termenbox/releases/tags/channel-beta` → parse version from release `body` or `name`.
- nightly: `GET /repos/termenbox/termenbox/releases/tags/channel-nightly` → parse version from release `body` or `name`.

Cache: 6 hours, `ETag`/`If-None-Match`, exponential backoff. Unauthenticated GitHub API limit is 60 req/hour per IP.

PWA bundle update (`updateAvailable` store) and server release notification are **separate** states. Reload button only appears for PWA updates.

### 7. Installer per-channel defaults

`install.sh` is built into each Pages deployment with channel-specific defaults:

```sh
# stable build
IMAGE="ghcr.io/termenbox/termenbox:latest"
RELEASE_URL="https://github.com/termenbox/termenbox/releases/latest/download"
ORIGIN="https://app.termenbox.dev"
RELEASE_KEYS="r1 ssh-ed25519 ..."

# beta build
IMAGE="ghcr.io/termenbox/termenbox:beta"
RELEASE_URL="https://github.com/termenbox/termenbox/releases/download/channel-beta"
ORIGIN="https://beta.app.termenbox.dev"
RELEASE_KEYS="r1 ssh-ed25519 ...\nb1 ssh-ed25519 ..."

# nightly build
IMAGE="ghcr.io/termenbox/termenbox:nightly"
RELEASE_URL="https://github.com/termenbox/termenbox/releases/download/channel-nightly"
ORIGIN="https://nightly.app.termenbox.dev"
RELEASE_KEYS="n1 ssh-ed25519 ..."
```

User can override with `TERMENBOX_RELEASE_URL`, `TERMENBOX_IMAGE`, `TERMENBOX_RELEASE_KEYS` env vars. The installer also accepts `--channel stable|beta|nightly` to select the channel at runtime (writes it to server config).

The installer's version parsing is fixed to extract the full SemVer string (not just `X.Y.Z`).

### 8. Docker images

- Stable tags push `latest`, `X.Y`, `X.Y.Z`.
- Beta tags push `beta`, `X.Y.Z-rc.N`, `X.Y.Z-beta.N`.
- Nightly tags push `nightly`, `X.Y.Z-nightly.YYYYMMDD`.
- `edge` is **not** introduced (unrequested fourth channel).
- Existing `:latest` users will stop receiving updates until the first stable tag after this change. Document in release notes.

### 9. `develop` branch workflow

- Created once from `master`.
- Feature PRs target `develop` (not `master`).
- Stable/beta tags are cut from `master` (which receives merges from `develop` before release).
- Nightly workflow runs on schedule (00:00 UTC) **and** on `workflow_run` completion of CI on `develop` (success), using the CI run's SHA. This avoids building from a red head.
- Branch protection on `develop`: required status checks, CODEOWNERS for `.github/workflows/**` and `release-keys.txt`.

### 10. Stable Pages deployment on tags

Stable client + Pages Functions deploy **only** on stable tag push. This means API/Functions fixes wait for a patch release. To keep patch releases cheap:

- `release.yaml` (or a new `release-stable.yaml`) builds client + server + manifest in one run.
- Patch version bump is a single commit + tag; CI is fast.
- Shared D1 migrations must be backward-compatible (additive only). Nightly/beta deployments apply migrations first; stable migration runs on tag deploy.

### 11. Nightly update mode: notify-only by default

Nightly channel default `mode = "notify"`. Auto-update requires explicit opt-in (`mode = "auto"` in config or `--auto-update` flag at install). This prevents daily surprise restarts on servers that just wanted to "try nightly".

### 12. Compatibility negotiation (future, not in v1)

Client and server exchange protocol version at `auth_ok`. Each declares the oldest peer it supports. Mismatch shows "Update your server" / "Reload the app". This is tracked in R50 but deferred to a follow-up.

### CI / Workflows

- `.github/workflows/release.yaml` → refactored into reusable `release-build.yaml` + three channel wrappers:
  - `release-stable.yaml`: `on.push.tags: ['v[0-9]*.[0-9]*.[0-9]*']` + gate job (core version match, tag on master, ancestry check). `environment: stable`. Publishes with `--latest`.
  - `release-beta.yaml`: `on.push.tags: ['v*-rc*', 'v*-beta*']` + gate (SemVer prerelease). `environment: beta`. Updates `channel-beta` alias. `--prerelease --latest=false`.
  - `release-nightly.yaml`: `on.schedule: ['0 0 * * *']` + `on.workflow_run` (CI on develop success). `environment: nightly`. Tag `vYYYY.MM.DD-nightly`, manifest version `X.Y.Z-nightly.YYYYMMDD`. Updates `channel-nightly` alias. Cleanup old nightlies (keep 14d, skip alias target). `--prerelease --latest=false`.
- `.github/workflows/docker-build.yaml`: reuse `release-build` artifacts; tag matrix per channel; push channel-specific tags.
- `.github/workflows/deploy-pages.yaml` → three workflows or one reusable with channel input; each deploys to its Pages project with channel-specific env.
- `.github/workflows/ci.yaml`: add `develop` branch triggers.

### Client

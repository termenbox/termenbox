## What was built (PR #245)

Server: the ACP backend now keeps a bounded, scrubbed stream per session (`acp_stream.rs`: Markdown replies, thoughts, tool calls merged by `toolCallId` with kind and status, diffs, the plan, permission requests and how they ended, notices) and serves it to a client that sends `acp_open` as batched `acp_view` messages (at most about 8 a second; a reset or a delta by revision and epoch). New client messages: `acp_prompt`, `acp_interrupt`, `acp_answer` (the exact option id the agent offered), `acp_mode` (only a mode the agent listed), `acp_close`. `answer` from Home or the inbox on a T0 prompt now reaches the agent by option id. `auth_ok` lists the allowlisted agents so New session can offer them. The companion shell needed nothing new on the server beyond the session's directory in the stream's info and `TERMENBOX_BACKEND=tmux,acp`: a plain tmux session `<name>-shell` is created with that directory.

Client: `AcpView.svelte` (header with the `T0 · ACP` label, mode list, context meter, search, copy, Shell; the stream; the prompt line), the decision card reused for an open permission, `lib/acpStream.ts` (the reducer, search, diffs), `lib/acpPrompt.ts` (slash completion, history, key row effects), `lib/markdown.ts` (a safe reader), `lib/acpStore.ts` (streams kept across session switches; draft, place and opened diffs kept across a reload).

## Why the stream is text in the page and not xterm.js

The deciding questions were scrolling, selecting and copying on an iPhone. xterm.js draws to a canvas (WebGL here): the page has no text to select, which is why the terminal already ships `SelectView.svelte` ("Touch screens cannot select text drawn by the terminal"), a second copy of the buffer as plain text. A stream we draw ourselves needs that on every line, not as a mode. Page text gives native selection handles, native momentum scrolling, the system Find, VoiceOver and Dynamic Type, links, and per-block Copy, and it is the same tokens and components as the rest (0110). What xterm gives (an ANSI emulator) is of no use: an ACP agent sends structured updates, not escape sequences. The cost is that long output is a DOM, so the stream is bounded (400 entries, 16 000 characters a reply, 512 KB on the server) and the open reply is parsed once per batched update. Evidence: the in-repo `SelectView` comment and the bounded-burst e2e; the iPhone scrolling and selecting itself is unverified until the owner's checklist.

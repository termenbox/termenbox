# R50 Release channels and auto-update policies for server and client
Status: superseded by R70
Score: V=7 T=5 R=7 S=8
Preds: none
Lane: free
Area: release
Platform: both
Was: new (owner request 2026-10-14)

Superseded by: R70 (full specification with three channels: stable, beta, nightly; per-channel keys; alias releases; compile-time version injection; separate Pages deployments; nightly notify-only default). Key differences: no `edge` channel; nightly from `develop` with date-based tag + SemVer manifest version; compile-time `TERMENBOX_RELEASE_VERSION` instead of build-once/promote; separate Pages projects per channel; nightly notify-only default; server channel via installer not web UI. See R70 for the authoritative plan.

Why: today there is one stable stream. `release.yaml` builds a signed manifest from an annotated `vX.Y.Z` tag; the server's daily updater (`updater.rs`, decisions 0063, 0076) installs it with rollback and honours a `freeze` flag; the hosted client is deployed from master by `deploy-pages.yaml`. The owner wants beta versions, untagged builds and tagged releases with clear update policies.
Recommended scheme (best practice; confirm with the owner before building, and record it as a decision):

1. Tag everything, with SemVer pre-release suffixes. `v0.2.0` is stable; `v0.2.0-beta.1` is beta; `v0.2.0-rc.1` is a release candidate. Never publish an untagged binary to users. Untagged work from master is an `edge` build named `v0.2.0-edge.<yyyymmdd>.<shortsha>` produced by CI on a schedule or on demand, not by hand, and never promoted without a tag.
2. Three channels, each its own signed manifest: `stable` (tags without suffix), `beta` (beta and rc), `edge` (edge). A new release goes to beta first; promoting to stable is publishing the same artifacts under a stable tag, so the binary that was tested is the binary that ships (build once, promote).
3. Per-server policy in the server config, changed from the app by the owner (root action by request file, decision 0077): channel (default `stable`), update mode `auto` (default), `notify` (show "update available", owner taps Update), or `hold` (pin the current version); a maintenance window (hour range, host time zone); and the existing `freeze`. Auto-update never moves a server to a lower channel's older version and never crosses a major version without the owner's tap.
4. Staged rollout: the manifest carries `rollout: <percent>`; a server updates when `hash(server_id) mod 100 < rollout`, so a bad release reaches few servers first and can be halted by a signed freeze. Rollback on a failed health check already exists.
5. Client: the hosted app has `app.` for stable and a beta deployment from Pages preview builds (free) for the beta channel, chosen by the owner in Settings and remembered per browser; self-hosted clients pin their own version. Service-worker updates apply on next launch with a "new version" toast, never mid-session.
6. Compatibility: client and server exchange a protocol version at `auth_ok`; each declares the oldest peer it supports. A mismatch shows "Update your server" or "Reload the app" and never silently misbehaves. Add a compatibility table to the docs.
7. GitHub Releases: beta, rc and edge are marked pre-release; the changelog is generated from Conventional Commits (skill `kms:changelog`).

## Do

Write the decision (channels, naming, policy defaults, rollout rule); extend `release.yaml` and the manifest format with `channel`, `rollout`, `min_client`; add policy fields and the channel check to `updater.rs`; add the Update settings screen; add protocol-version negotiation; document in README and `SECURITY.md`.

## Done when

A beta tag produces a signed beta manifest that only beta servers install; a stable server ignores it; a server set to `hold` or `notify` does not update on its own; a release at `rollout: 10` reaches about one tenth of test server ids; a client older than `min_client` shows the update message; guardrails `releases-are-signed` and `updates-are-verified-and-reversible` still hold (tests).

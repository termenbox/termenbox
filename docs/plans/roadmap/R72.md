# R72 Find in terminal: bounded tmux history snapshot searched in the browser
Status: pending

Preds: none

Platform: both
Was: R59 spike result, docs/plans/assets/terminal-search/feasibility.md

## Why

Finding earlier agent output needs history, and the browser has none: tmux runs in the alternate screen, so xterm keeps only the visible rows and rebuilds them on every attach. R59 showed the history exists in tmux and can be fetched and searched cheaply.

## Context

`docs/plans/assets/terminal-search/feasibility.md` has the measurements, the option comparison and the acceptance criteria this step implements. `backend.rs` `capture` reads the visible pane only. `e2e/search.mjs` is the experiment to promote. Separate from R43 (paid cloud history): nothing is stored.

## Do

1. Add an optional `history(id, window, rows)` to `SessionBackend` (tmux: `capture-pane -p -J -S -N -t <pane id>`, capped at 5000 rows and 1 MB) and a request/response pair in `termenbox-core`; backends without it answer "unsupported".
2. Add a Find panel (desktop and phone width) that fetches the snapshot when opened, matches case- and accent-insensitively in the page, shows hits with context and the "last N lines" bound.
3. Bind results to server, session, window and pane id; label them "older than the screen" when output arrives, offer refresh, clear them on session or window change, reattach or a missing pane.
4. Inside a full-screen program (`alternate_on`) or on a non-tmux backend, say so and search the current screen only.
5. Promote `e2e/search.mjs` into the feature's e2e with the acceptance criteria from the feasibility note.

## Done when

The six acceptance criteria in `feasibility.md` pass in the Chromium e2e job, and the query string is absent from every server-bound message and log.

## Check

**Class:** implement

`cargo test --workspace`, `pnpm -r test` and the Chromium e2e job pass, with the e2e asserting a token that scrolled out of view in real tmux is found and that no frame sent to the server contains the query.

## Notes

The searched text comes from the server; do not describe the feature as device-only. A server-side search, if ever added, sends the query to the owner's server and must say so.

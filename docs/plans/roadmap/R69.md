## Why

The client deploys to one Cloudflare Pages project from every push to master. A beta or nightly server needs a matching client, and a PWA service worker, its caches, localStorage and the OAuth callback are all bound to an origin, so channels need separate origins, not `/beta/` paths.

## Context

| Channel | Domain | Pages project | Build env |
|---|---|---|---|
| stable | `app.termenbox.dev` | `termenbox` | `VITE_CHANNEL=stable` |
| beta | `beta.app.termenbox.dev` | `termenbox-beta` | `VITE_CHANNEL=beta` |
| nightly | `nightly.app.termenbox.dev` | `termenbox-nightly` | `VITE_CHANNEL=nightly` |

All three share one D1 database, `CERT_SIGNING_KEY` and `DIRECTORY_SALT`; the GitHub OAuth client id and secret are per environment. Stable deploys only on a stable tag, so a Pages Functions fix waits for a patch release: D1 migrations must stay additive, and beta and nightly apply them first. `install.sh` is built into each deployment with its channel's image, release URL, origin and key list (`r1`; `r1`+`b1`; `n1`). This must stay inside the Cloudflare free budget (fact 0022) and decision 0108.

## Do

1. `packages/client/vite.config.ts`: define `VITE_CHANNEL`, `VITE_API_ORIGIN`, `VITE_APP_VERSION`, `VITE_GITHUB_CLIENT_ID`.
2. Replace `deploy-pages.yaml` with one reusable deploy workflow taking a channel, called by the three release workflows of R68; stop deploying stable from master pushes.
3. `infra/termenbox-cloud/`: the beta and nightly projects and DNS.
4. Build the per-channel `install.sh` defaults.
5. Decision to record: three Pages deployments on separate origins, stable on tags only.

## Done when

A beta tag deploys `beta.app.termenbox.dev` with the beta installer and `VITE_CHANNEL=beta`; a stable tag deploys `app.termenbox.dev`; a push to master deploys nothing; the beta installer's key list is `r1` and `b1` and the nightly one's `n1`; the request budget check (R07) still passes.
